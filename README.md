# Architecture

## Структура платформы для решения задач математического анализа

Система предназначена для обработки большого количества задач с контролем нагрузки и устойчивостью к сбоям.

Каждая задача:
- попадает в очередь,
- обрабатывается рабочими процессами (воркерами),
- система автоматически регулирует свою скорость, чтобы не перегружаться.

## Ответы на вопросы
### Чем отличаются Kafka и RabbitMQ

|Критерий|Kafka|RabbitMQ|
|---|---|---|
|Как передаются сообщения|Клиент сам забирает сообщения|Сервер сам отправляет сообщения|
|Контроль нагрузки|Хороший — клиент сам регулирует скорость|Хуже — сервер может «залить» клиента|
|Хранение сообщений|Хранит историю, можно перечитать|Удаляет после обработки|
|Подходит для|Потоков событий, аналитики, больших нагрузок|Быстрых задач, RPC, уведомлений|
|Масштабирование|Простое и линейное|Сложнее при больших нагрузках|

### Коротко:
- **Kafka** — это журнал событий, который можно читать сколько угодно раз и с любой скоростью.
- **RabbitMQ** — это очередь доставки задач, где главное — быстро передать и удалить.

---

### Подход к обработке задач

Используется схема:

> **Очередь задач + пул воркеров**
- Очередь хранит задачи.
- Воркеры берут задачи и выполняют их.
- Специальный контроллер следит за нагрузкой и регулирует количество воркеров.
---

### Контроль нагрузки
Контроллер измеряет загрузку процессора (CPU) и действует так:

`если CPU < 60% → увеличиваем число воркеров
если CPU > 80% → уменьшаем число воркеров
`

Это позволяет:
- не перегружать сервер,
- не терять производительность,
- сохранять стабильность.
---
### Почему выбран Kafka

Kafka выбрана потому что она позволяет:
- контролировать скорость обработки,
- безопасно переживать сбои,
- перечитывать сообщения при ошибках,
- легко масштабироваться.
RabbitMQ хорош для быстрых запросов и ответов, но сложнее управляется при высокой нагрузке.
---
### Саморегуляция системы
Если нагрузка становится слишком высокой:
1. Замедляется чтение новых задач из очереди.
2. Уменьшается количество воркеров.
3. Очередь начинает накапливать задачи вместо того, чтобы перегружать сервер.
Таким образом система **сама себя стабилизирует**.
---

### Масштабирование
#### Между серверами:
- Kafka автоматически распределяет задачи между экземплярами сервиса.
- Kubernetes (или другой оркестратор) добавляет или убирает серверы по нагрузке
#### Внутри одного сервера:
- Количество воркеров подстраивается под число ядер процессора.
- Используются буферизированные очереди, чтобы избежать простоя.

---

## Общая идея системы

> **Цель не в том, чтобы обработать максимум задач любой ценой, а в том, чтобы система оставалась стабильной, управляемой и предсказуемой при любой нагрузке.**
